# Project context — slippery-executives

Read this first. It captures what the project is, the full plan, every
design decision made so far and why, and the current state of the code.
Style/build conventions live in `CLAUDE.md` (authoritative for how to
write code); this file is authoritative for *what we're building and
where we are*. Keep both current: update the "Current state" and
"Roadmap" sections at the end of each working session.

## One-sentence pitch

A networked historical execution laboratory where users upload the trade
instructions generated by an alpha strategy, run those instructions
through configurable TWAP, VWAP, POV, or implementation-shortfall
algorithms in a market calibrated to historical stock data, and measure
how much theoretical alpha survives after realistic execution costs.

## What the product is

The user's alpha model (which we never see) has already decided *what*
to trade. They upload its output — a CSV of timestamped instructions:

```
timestamp,symbol,side,quantity,deadline
10:05:00,NVDA,BUY,50000,11:00:00
10:30:00,AMD,SELL,20000,12:00:00
```

They then pick a supported symbol, a historical trading date, starting
cash/positions, one of four execution algorithms, and that algorithm's
parameters. The platform simulates executing those instructions against
that day's market and reports how much of the alpha's theoretical P&L
survived execution costs. Multiplayer: several users run the same
instructions/market with different execution choices and compete on a
leaderboard.

Core flow:

```
alpha CSV → parser/validator → instructions → parent-order manager
  → execution algorithm → child orders → fill engine → fills
  → portfolio/P&L → transaction-cost analytics → results/leaderboard
```

When an instruction's time arrives, a *parent order* activates. The
selected algorithm slices it into *child orders* (submit / cancel /
replace) over time until filled or the deadline expires.

## The four execution algorithms

All implement one interface: on every market update they receive the
time, market state, parent-order state (filled/working/remaining
quantity, time remaining) and return actions (submit/cancel/replace
child order, or do nothing).

- **TWAP** — pure schedule: split evenly across time intervals,
  regardless of market activity. Config: interval count/length, child
  size, passive timeout, catch-up behavior.
- **VWAP** — schedule shaped by the *historical* intraday volume
  profile: trade more when the market is typically busy (open/close).
  Promises when you finish; doesn't bound your share of real volume
  (hence a max-participation safety cap). Config: volume buckets,
  profile, max participation, recalc frequency.
- **POV** — no schedule: react to *observed* volume, staying at X% of
  whatever actually trades. Promises your market share; doesn't promise
  a finish time (hence deadline catch-up behavior). Config:
  participation rate, volume window, min/max child size, catch-up.
- **Implementation Shortfall** — dynamically trades off impact cost
  (from trading fast) against drift/opportunity cost (from trading
  slow), using time remaining, schedule deficit, price movement,
  spread, volatility. Config: risk aversion, max participation, passive
  timeout, price sensitivity, deadline urgency.

Key VWAP-vs-POV distinction: VWAP follows *forecast* volume, POV
follows *realized* volume. They fail differently on abnormal days.

## Market simulation: one interface, two fill engines

We use free 1-minute OHLCV bars (open/high/low/close/volume per minute)
for a curated set of symbols/dates. Bars determine price movement,
volume, volatility, intraday volume pattern, approximate spread. We do
NOT claim to reconstruct the real order book — the honest product
description is "execution strategies run in a synthetic market
calibrated to a real historical session."

Both engines sit behind the same interface (conceptually
`on_child_order : t -> Child_order.t -> Fill.t list` and
`on_bar_advance : t -> Market_bar.t -> Fill.t list`), so algorithms
never know which world they're trading in.

### Engine A: bar-based fill model (MVP)

Stateless calculator — no book exists. Rules per child order + bar +
config:

- Aggressive orders fill at bar price ± synthetic half-spread ± impact
  penalty. The BBO is *fabricated* around the bar price (`Bbo.t`).
- Limit orders fill only if the bar trades strictly *through* the price
  (`low < limit` for buys — strict, to partially offset the missing
  queue model).
- Fill size capped at a configurable % of bar volume (participation
  cap).
- Market impact = penalty function of (order size / bar volume),
  square-root shape is standard.

Known, documented approximations (all are config knobs in a
`Fill_model.Config.t`): invented spread (should later scale with bar
range), unknown intra-bar price path (pick a convention; algorithms
must only see the *previous* bar when deciding — no look-ahead),
optimistic passive fills (no queue position / adverse selection),
participation cap as a liquidity stand-in, stateless impact (no memory
across bars). These distort absolute cost identically for everyone, so
*rankings and value-add vs. baseline remain meaningful* — that's the
product's actual promise (fair comparison, not "your true P&L").

Because fills happen on bars, the sim clock effectively ticks
per-minute and algorithms decide at bar boundaries. Don't let code
secretly assume finer granularity.

### Engine B: synthetic exchange (phase 3)

A real limit order book + matching engine (reuse jsip-exchange's book
and matching engine — see below) populated by *background agents*
calibrated to the bars: they quote around the historical price path
(the bar path plays the role of jsip's `fundamental_oracle` value),
post depth consistent with bar volume, widen with bar range. Client
child orders match against agent orders through real price-time
priority — so queue position, depth exhaustion, and market impact
*emerge mechanically* instead of by formula. Agents lean against
deviations, pulling the sim price back to the historical path (impact
is real but temporary). Leash tightness is the key calibration
parameter. Killer invariant/test: run with zero client orders → sim
VWAP ≈ historical VWAP. Stochastic → consumes the run's random seed;
same seed = same fills (deterministic replay requirement).

## Analytics (the point of the whole thing)

Costs quoted in basis points (1 bp = 0.01%). Key concepts:

- **Arrival price** — market price at the instant the instruction
  activated; the decision-moment benchmark.
- **Implementation shortfall** — (avg execution price − arrival price)
  as bps of arrival; the headline "how much did execution friction
  eat" number.
- **Spread cost** — sum of the half-spread tolls paid on
  liquidity-*taking* fills (minus rebates earned on providing fills).
  Requires `Fill.liquidity` (Taker/Maker), recorded at fill time
  because it can't be reconstructed later.
- **VWAP slippage** — avg execution price vs. the day's market VWAP:
  did you trade worse than the crowd?
- **Completion rate / opportunity cost** — unfilled shares of a correct
  alpha are pure lost alpha.
- **Alpha capture** — net P&L / gross theoretical P&L. Gross
  theoretical P&L must be defined precisely: every instruction fills
  instantly and fully at the arrival price with zero cost.
- **Execution value-add** — algorithm net P&L − naïve-baseline net
  P&L. Baselines every run is auto-tested against: immediate full
  execution (primary naïve), equal-sized aggressive, passive-only,
  random scheduling.

## Multiplayer & leaderboard

- **Fixed-alpha challenge** — same alpha file, symbol/date, capital,
  market seed for everyone; users differ only in execution
  algorithm/config. Isolates execution skill. Rank by shortfall, net
  P&L, alpha captured, completion, cost, or combined score.
- **Open-strategy challenge** — users upload their own alpha files too;
  results must display alpha quality and execution efficiency
  *separately*.

Users' runs are separate simulations against the same market
conditions — users' orders never interact (a true shared market is a
stretch goal). Live dashboard during a run: market panel, parent-order
panel, child-order blotter, event log, live analytics. Final screen:
gross alpha P&L, naïve net, algo net, value added, alpha captured,
completion, shortfall, VWAP slippage, plus side-by-side algorithm
comparison.

## Architecture decisions made so far (with rationale)

1. **Core-first, networking last.** The original plan put the server in
   the MVP; we deliberately deferred it. Build the simulation as a
   pure, deterministic library driven by a single-machine CLI; wrap
   Async RPC around it once it works. Debugging market-sim bugs through
   a network protocol is the failure mode we're avoiding. Real MVP
   milestone: one instruction CSV + one day of bars → TWAP → slippage
   report in the terminal, identical output every run.
2. **Times of day, not timestamps.** Alpha CSVs contain times
   (`10:05:00`), so `Alpha_instruction` uses `Time_ns.Ofday.t`
   (exchange-local). This keeps the parser independent of run config
   and makes instruction files date-independent (replayable against any
   bundled date — exactly what fixed-alpha challenges need). Absolute
   time appears only when a run binds instructions to a session date.
   Field is named `arrival_time` conceptually (it anchors
   arrival-price slippage).
3. **Relationship to jsip-exchange** (`/home/ubuntu/jsip-exchange`, a
   separate full exchange project we selectively mine). jsip *is* a
   market: an authoritative venue matching real counterparties. This
   project *models* a market: a lab answering "what would the market
   have done to these orders" and grading the result. The matching
   engine is a mechanism inside a market; a fill engine is a stand-in
   for a whole market. In phase 3, jsip's matching engine gets reused
   as an internal component of our fill engine.
4. **Type ledger** (kept/dropped from jsip, all in `lib/types/src/`):
   - Kept as-is: `Price` (int cents), `Side`, `Size`, `Symbol`,
     `Order_id` (+ sequential `Generator` — deterministic, replay-safe),
     `Level`, `Bbo` (synthetic BBO fabrication + dashboard spread).
   - Dropped `Client_order_id`: it solves a client/server ID race that
     doesn't exist here — our users never submit orders; child orders
     originate inside the simulation with IDs assigned synchronously.
   - Dropped `Participant`: fills have no real counterparty; run/room
     ownership identifies whose fill it is. Reintroduce only for the
     shared-market stretch goal.
   - Rebuilt `Fill` backtester-centric: an execution event on one of
     *our* child orders — `fill_id, order_id, symbol, side, price,
     size, time : Time_ns.Ofday.t, liquidity : Liquidity.t`. Gained
     `time` (analytics is fill-driven) and `liquidity`
     (`Taker | Maker` — powers spread-cost attribution); lost the
     aggressor/resting dual-party fields. One child order may produce
     several fills; engines return `Fill.t list`.
   - To adapt later: `Time_in_force` (`Day`/`Ioc` maps to
     passive-rest vs aggressive child orders), `Cancel_reason` (our
     causes: passive timeout, algorithm replaced, deadline expired,
     end of day), the `Order.Request`-vs-live-order split (pattern for
     `Child_order`: immutable request + mutable remaining size),
     jsip's `order_book`/`matching_engine`/bot runtime (phase 3).
   - Skipped: gateway, sessions, participant registry, exchange_event
     (our `server_event` will be differently shaped).
5. **Validation split.** Row-level invariants (positive quantity,
   deadline after arrival) belong in
   `Alpha_instruction.create : ... -> t Or_error.t` (smart
   constructor); context checks (symbol supported, market hours,
   capital) live in the parser/validator layer which has the config.
6. **Open questions.** Whether to add a `Money.t` (int cents) distinct
   from `Price.t` for cash/notional (decide when the portfolio engine
   lands); whether `Time_in_force` stays a separate `Child_order` field
   or nests inside `Order_type.Limit`'s payload; extracting the
   market-hours constants (duplicated in `alpha_instruction.ml` and
   `trading_day.ml`) into a shared `Market_hours` module. Settled:
   `Liquidity` is `Taker | Maker`; `deadline = arrival_time` is legal;
   statistics about prices are `float` while tradeable prices are
   `Price.t`; `Size.t` is the unit "shares" (used for bar volume too).

## UI design (hand-sketched 2026-07-28)

Seven screens; wizard flow is
`Day -> Alpha -> Algo -> Confirm -> Simulate -> Results`.

1. **Main dashboard** — ExecLabs branding, a big "Run Simulation"
   button, Recent Runs (e.g. "NVDA 3/15 TWAP 81.5% captured") and Best
   Runs lists. Login/auth is a later concern.
2. **Choose market day** — calendar showing only (symbol, date) pairs
   we have data for, with a preview chart of the data leading up to
   that day. Day is chosen *first* so every later step can validate
   against it.
3. **Upload alpha CSV** — drag-and-drop; immediately shows the parsed
   instruction table, or line-numbered errors.
4. **Select algorithm** — TWAP / VWAP / POV / IS with per-algorithm
   parameter forms and plain-language explanations.
5. **Review & start** — summary of day / alpha / algorithm, start
   button.
6. **Simulator (live)** — sim clock with playback controls (pause,
   1x/2x/10x), percent-of-day progress, price chart, parent-order
   panel (filled/total), child-order blotter, event log.
7. **Results/analytics** — the metric tree, plus a *same-strategy
   leaderboard* comparing algorithms on this exact day+alpha (e.g.
   VWAP 80.7% / TWAP 60.6% / POV 30% alpha captured), with "retest
   with a different algo" and "new sim" actions.

Design consequences (bind these before building the driver):

- The engine must support both *instant* batch runs (baselines,
  retests) and *paced playback* with a speed multiplier: the engine
  exposes step-on-demand; a playback controller owns cadence. Never
  bake wall-clock pacing into the simulation core.
- "Retest" reruns a stored config with a different algorithm, so runs
  (config + results) need lightweight persistence (sexp files are
  fine) — this also feeds Recent/Best runs and the leaderboard.
- The MVP leaderboard is *local, same-strategy, cross-algorithm*; the
  fixed-alpha multiplayer variant arrives with the server later.
- `Data_loader` needs a discovery function (list available
  symbols/dates) to drive the calendar screen.
- The client is a GUI; likely stack is a Bonsai web app (Bonsai and
  frontend-design skills live in `.claude/skills`). The MVP stays
  CLI-driven until the core works end to end.

Implemented UI (merged to `main`, lives in `app/ui`): a Bonsai replay
client that runs the whole simulation in the browser off embedded data
(TSLA 2026-07-09 + the demo alpha), then replays the deterministic
result on a clock. Layout: header with the exact engine command,
replay controls (speed pills + scrubber), an annotated SVG line chart
(shaded per-order windows, dashed arrival and day-vwap reference
lines, per-order fill tick rows, optional fill-price dot overlay),
live total P&L (execution benefit revealed only at the close, to avoid
spoilers), per-order stat cards with live side-adjusted shortfall/vwap
bps, and a columnar monospace fill blotter. Styling is a first-class
theme record (`Styles.t`) with two palettes — `paper` (warm light) and
`dark` (blue-black terminal) — behind a runtime toggle. Color rules:
green/red mean good/bad execution only, order identity gets its own
hue palette, buy/sell stays neutral. Iterated 2026-07-29/30 through
several designs (dark violet terminal, soft light, toned-down light,
paper, dark); the toggle version superseded them all and the
experiment branches were deleted.

UI backlog:

- The results screen (screen 7): metric tree, cost decomposition
  waterfall, same-day algorithm comparison table.
- Hover tooltip panel (SVG <title> is the cheap interim), wheel
  zoom/pan, click-an-order-to-filter.
- Real data selection (symbol/date/alpha upload) instead of the single
  embedded day; js_of_ocaml --release profile to shrink the ~64MB dev
  bundle.

`lib/simulation` is its own library (not part of `lib/market` as
originally planned) because `fill_model` needs both `lib/market` and
`lib/execution` — putting it in either would create a cycle.

Each lib follows the CLAUDE.md layout (`lib/<x>/src` + `lib/<x>/test`,
library `execlab_<x>` / `execlab.<x>`) with a top-level re-export
module like `lib/types/src/execlab_types.ml`.

Engine A, the driver, TWAP + Immediate end to end) are DONE — the MVP
milestone shipped, and a first cut of the client UI (originally item
8) landed early. What remains, in order:

   into spread + impact + timing/drift + opportunity inside
   `Transaction_cost` — the engine's `half_spread` and impact
   coefficient make each term exactly computable (needs `Trading_day`
   and `Fill_model.Config` as inputs). Encode "components sum to total
   shortfall" as a hand-computed expect test.

   (2026-08-03, see current state). VWAP (TWAP with the schedule
   following `Day_stats.volume_profile`) is implemented on the
   unmerged `ui7` branch — merge it to main. Then implementation
   shortfall (needs an urgency model — hardest, last). POV's rolling
   volume-window smoothing knob is still open.

   decomposition, benchmark table, same-day algorithm comparison.
4. Run persistence (config + results as sexp files) and the local
   same-strategy leaderboard; "retest with a different algo" flows
   from stored configs.
5. Server split (Async RPC at the one client<->server seam): real
   symbol/date selection and alpha CSV upload replace embedded data;
   the multiplayer fixed-alpha leaderboard arrives here.
